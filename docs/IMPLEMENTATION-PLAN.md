# SafeNet KZ — план внедрения и развития / енгізу және даму жоспары

> **Принцип.** Система не объявляет схему незаконной. Она выявляет признаки возможного нарушения. Законность проверяет человек с учетом законодательства РК.

**Қысқаша (қазақша).** Енгізу үш кезеңнен тұрады: пилот → интеграция → масштаб. Пилотта жүйе тек ашық деректерде жұмыс істейді. Алдымен «көлеңкелі» режимде нақты сапа өлшенеді, кейін талдаушылар кезекпен жұмыс істейді. Олардың шешімдері ережелер мен модельді жақсартуға қайтарылады. Масштаб үшін тексеру stateless воркерлерде хабарлама кезегінің артында көлденең кеңейтіледі. Барлық қадам ҚР заңнамасы, дербес деректерді қорғау және платформа ережелері шеңберінде жасалады. Шешімді әрқашан адам қабылдайды.

Сроки ниже — ориентировочные плановые допущения, а не обязательства. Все качественные цифры v5 получены на **синтетических** данных (см. [METHODOLOGY.md](METHODOLOGY.md#14-метрики)). Первая задача пилота — измерить качество на реальных открытых данных.

## 1. Исходная точка: что уже есть в v5

| Уже работает | Ещё не проверено |
|---|---|
| Автоматический конвейер: правила `rules-v5` + n-граммная модель → сетевое обогащение → очередь (балл ≥ 30) / автоматическое отсеивание | Качество на реальном потоке: вся оценка синтетическая, классы сбалансированы |
| Интерфейс аналитика: «Пульт», «Очередь проверки» с досье, «Автопоток», «Сети и связи», «Качество» | Работа в многопользовательском режиме: нет ролей, SSO и общей БД; хранилище — локальные JSON-файлы |
| Решения с причинами и обратная связь `/api/review-stats` | Коннекторы к API платформ: соглашений нет |
| Реальные источники: открытые Telegram-каналы (Watchtower), расширение браузера, ручная проверка, пакетный API `POST /api/screen` (до 500 материалов, ничего не сохраняет) | Проверка казахских формулировок и транслитерации носителями языка |
| Скорость ≈ 1 600 материалов/с на одном потоке (правила + модель, без OCR/ASR/ИИ), 265 автотестов | Нагрузка на OCR/ASR/LLM при реальном объёме медиа |

## 2. Этапы

### Этап 0. Подготовка (≈ 1 месяц)

1. **Заказчик и правовая основа.** Определить ведомство-партнёра, полномочия, в рамках которых работает аналитик, и что значит «Передать в ведомство» (адресат, формат, сроки).
2. **Юридическая экспертиза.** Перечень разрешённых открытых источников, условия использования платформ, режим персональных данных, сроки хранения, порядок передачи материалов. Отдельно: можно ли обрабатывать групповые чаты, переданные гражданами, и как.
3. **Регламент аналитика.** Определения признаков по трём трекам из брифа. Критерии решений «Подтвердить признаки» / «Передать в ведомство» / «Ложное срабатывание». Справочник причин отклонения (в интерфейсе уже есть: бесплатный конкурс, легальная реклама, новость или предупреждение, недостаточно признаков, другое).
4. **Экспертный корпус.** Собрать материалы из разрешённых открытых источников и разметить двумя независимыми разметчиками. Спорные случаи — через юриста. Казахские и транслитерированные примеры проверяет носитель языка. **До начала любой настройки отложить и заморозить экспертный holdout.**
5. **Развёртывание.** Сервер на инфраструктуре заказчика. Анализ, OCR, ASR и локальная модель Qwen3-VL работают без внешних облачных API, поэтому данные не покидают контур.

### Этап 1. Пилот (≈ 2–3 месяца, одна команда аналитиков, только открытые данные)

1. **Источники:** мониторинг открытых Telegram-каналов, расширение браузера у аналитиков, ручная проверка обращений, `POST /api/screen` для выгрузок. Демо-поток отключается или остаётся только для обучения сотрудников; демо-случаи и так помечены «демо».
2. **Теневой режим (первые недели).** Конвейер работает, а эксперты размечают его выход и случайную выборку отсеянного, не влияя на текущую работу. Результат — **базовая линия** на реальных данных: precision очереди, оценка recall, FPR по типам контента, разрезы по трекам и языкам.
3. **Калибровка.** Выбрать порог очереди и порог модели по кривой «порог → precision / recall / FPR» на реальной разметке. Сейчас пороги 30 и 0,5 выбраны на синтетике.
4. **Рабочий режим.** Аналитики разбирают очередь по приоритету. Каждое решение сохраняется с причиной, комментарием и временем до решения.
5. **Еженедельный разбор обратной связи** по `/api/review-stats` (раздел 6).
6. **Регулярный аудит отсеянного.** Эксперт размечает случайную выборку автоматически отсеянных материалов. Это единственный способ оценить пропуски на реальном потоке.
7. **Выпуски версий.** Новая версия правил или модели выходит только после проверки на замороженном экспертном holdout. Версия правил записывается в каждый случай (`analysisVersion`), версия модели — в `analysis.model.version`.

### Этап 2. Интеграция (≈ 3–6 месяцев)

1. **Коннекторы по соглашениям:** официальные API и исследовательский доступ платформ, рекламные библиотеки. Необязательный коннектор Meta Ad Library API уже есть. Для TikTok Research API нужен одобренный доступ.
2. **Встраивание в системы ведомства** через `POST /api/screen` и экспорт доказательств: JSON с SHA-256 канонического содержимого уже реализован.
3. **Многопользовательский режим:** БД вместо JSON-файлов (сейчас лимит — 5000 кейсов), роли и SSO, журнал аудита действий, распределение очереди между аналитиками.
4. **Второй этап на LLM для пограничных случаев:** балл около порога, случаи «только модель», смешанный контекст. В проекте уже есть локальная Qwen3-VL через Ollama. LLM даёт пояснение и второе мнение, а не решение. Её вклад оценивается на holdout так же, как вклад n-граммной модели.
5. **Активное обучение:** отдельная очередь разметки из неуверенных случаев (раздел 6).

### Этап 3. Масштаб

1. Переход на архитектуру из раздела 3, нагрузочные тесты.
2. Мониторинг дрейфа: появление нового сленга, падение доли подтверждений по сигналу, рост доли «только модель».
3. Новые платформы и сценарии по запросу ведомства, каждый — с отдельной оценкой.

## 3. Инфраструктура для масштаба

```
коннекторы: Telegram, API платформ, рекламные библиотеки, обращения граждан
        │
        ▼
очередь сообщений (тема raw-items, дедупликация по каноническому URL + хешу нормализованного текста)
        │
        ├──► stateless-воркеры скрининга × N — правила + модель, тот же код, что в POST /api/screen
        │          │
        │          └──► пул медиа-воркеров (OCR / ASR / Qwen3-VL) — только для материалов с изображением, видео или звуком
        ▼
сервис сетевого обогащения — общий индекс «индикатор → аккаунты», LSH-корзины шаблонов
        │
        ▼
маршрутизатор:  балл ≥ порога → БД очереди (приоритет)  ·  ниже порога → журнал с коротким сроком хранения
        │
        ▼
интерфейс аналитиков → решения → хранилище обратной связи → пересмотр весов / переобучение → новая версия
```

- **Горизонтальное масштабирование скрининга.** Анализ одного материала не зависит от других, поэтому воркеры не хранят состояние. Пропускная способность растёт добавлением воркеров за очередью сообщений. Ориентир для расчёта — измеренные ≈ 1 600 материалов/с на поток (≈ 138 млн текстов в сутки на ядро) без OCR/ASR/ИИ. Число воркеров = пиковый поток ÷ (1 600 × запас). Подходит любой брокер (например, Kafka, RabbitMQ, NATS).
- **Медиа — отдельный пул.** OCR, ASR и визуальная модель на порядки дороже текстового скрининга. Их запускают только для материалов с медиа и масштабируют отдельно, при необходимости на GPU. Сырые кадры и звук не хранятся: сохраняется только распознанный текст с временными отметками (так уже работает расширение).
- **Пакетный API.** `POST /api/screen` (до 500 материалов за запрос, без сохранения) подходит для интеграций по модели «pull» и для разовых выгрузок.
- **Состояние — только в сетевом индексе.** Сейчас индекс живёт в памяти процесса, и демо-конвейер пересчитывает кластеры на каждое событие. Поэтому в живом конвейере ≈ 3,6 мс на событие против 0,63 мс у чистого скрининга. Для масштаба индекс выносится в общее хранилище (например, PostgreSQL или Redis): union-find обновляется инкрементально, LSH-корзины хранятся как ключи.
- **Хранилище:** реляционная БД для случаев, решений и журнала аудита. Отсеянные материалы не создают кейс; журнал хранится ограниченное время.
- **Наблюдаемость:** пропускная способность, задержка от публикации до очереди, длина очереди, доля автоматически отсеянного, доля подтверждений по сигналам, трекам и языкам.
- **Безопасность:** доступ по ролям, шифрование хранилища, журнал доступа к случаям.

## 4. Роли

| Роль | Задачи |
|---|---|
| **Аналитик** | разбирает очередь, принимает решения с причиной и комментарием, отмечает спорные случаи |
| **Старший аналитик / методолог** | ведёт регламент, еженедельно разбирает `/api/review-stats`, предлагает изменения весов и правил, контролирует качество разметки |
| **Юрист** | правовая основа, оценка законности по законодательству РК для переданных случаев, персональные данные, условия платформ, соглашения на коннекторы |
| **Data engineer** | коннекторы, очередь сообщений, хранилище, дедупликация, сроки хранения, мониторинг инфраструктуры |
| **ML-инженер** | переобучение модели, активное обучение, калибровка порогов, проверка версий на holdout, мониторинг дрейфа, второй этап на LLM |
| **Лингвист, носитель казахского** | проверка казахских правил, транслитерации и разметки, сбор казахских трудных отрицательных примеров |
| **Координатор с ведомством** | приоритеты, формат передачи случаев, обратная связь о том, какие переданные случаи приняты в работу |

## 5. Данные, этика, право

- **Только открытые данные.** Публичные публикации и каналы, рекламные библиотеки, официальные API по соглашениям. Без закрытых чатов, без обхода ограничений доступа, без фиктивных аккаунтов для проникновения в группы. Групповые чаты — только переданные законно (например, обращение гражданина или экспорт участника, который вправе им поделиться).
- **Персональные данные.** Соблюдение законодательства РК о персональных данных и их защите. Минимизация: кейс создаётся только для материалов из очереди, отсеянные остаются в журнале ограниченное время, номера карт хранятся замаскированными (первые 4 и последние 4 цифры — уже реализовано). Установленный срок хранения, доступ по ролям, журнал доступа.
- **Правила платформ.** Сбор — в пределах условий использования и лимитов; масштабный сбор — только через официальные API и соглашения.
- **Признаки, а не вердикты.** Система не блокирует, не публикует и не обвиняет. Каждое решение принимает человек, а оценку законности делает юрист с учётом законодательства РК. Должна быть процедура исправления ошибочного решения.
- **Справедливость по языкам.** На синтетике precision на казахском (75,0%) ниже, чем на русском (93,8%). Метрики ведутся отдельно по языкам, а казахские правила проверяют носители языка.
- **Прозрачность.** Методология, версия правил и версия модели известны для каждого случая; каждый сигнал объясним цитатой.
- **Синтетика отдельно от реальных данных.** Демо-случаи помечены «демо» и не смешиваются с реальными в отчётности.

## 6. Человек в контуре: цикл обратной связи

1. **Решение.** Аналитик выбирает «Подтвердить признаки», «Передать в ведомство» или «Ложное срабатывание» с причиной. Сохраняются решение, причина, комментарий и время до решения.
2. **Агрегация.** `GET /api/review-stats` считает долю подтверждений по каждому сигналу, по трекам и по причинам отклонения, а также медианное время до решения.
3. **Еженедельный разбор у методолога:**
   - сигналы с низкой долей подтверждений — кандидаты на снижение веса или уточнение шаблона;
   - частая причина «новость или предупреждение» — материал для доработки контекстных правил;
   - частая причина «бесплатный конкурс» — уточнение правил трека 1.
4. **Активное обучение.** В приоритет разметки попадают случаи, где система менее уверена: балл около порога, случаи «только модель», расхождение правил и модели. Размеченные случаи пополняют обучающий пул модели.
5. **Выпуск.** Новая версия правил или модели проверяется на замороженном экспертном holdout. Она выходит, только если precision и FPR не ухудшились ни по одному треку и языку. На holdout никогда не обучают и не настраивают.
6. **Аудит отсеянного** — регулярная оценка пропусков на реальном потоке.

## 7. KPI пилота

Целевые значения устанавливаются после теневого режима по реальной базовой линии. Синтетические цифры v5 приведены только как ориентир: на реальном потоке, где рискованных материалов меньше, precision ожидается ниже.

| KPI | Как измеряется | Ориентир v5 (синтетика) |
|---|---|---|
| Precision очереди | доля «Подтвердить» + «Передать» среди решений (`/api/review-stats`), по трекам и языкам | 85,5% (holdout) |
| Оценка recall | экспертный holdout + аудит случайной выборки отсеянного | 74,7% (holdout) |
| FPR по типам контента | причины отклонения + экспертная разметка трудных отрицательных примеров | 12,3% (holdout); новости и предупреждения — 4 из 13 |
| Снижение нагрузки | доля автоматически отсеянного | 44,8% на демо-потоке |
| Время аналитика | медианное время до решения | измеряется в пилоте |
| Задержка | от публикации до появления в очереди | измеряется в пилоте |
| Полезность для ведомства | доля переданных случаев, принятых ведомством в работу | измеряется в пилоте |
| Разрыв по языкам | precision и recall для казахского и транслитерации против русского | KK P 75,0%; translit R 53,9% |
| Надёжность модели | доля подтверждений у случаев «только модель» | 77,8% (holdout) |
| Покрытие | число источников и материалов в сутки | измеряется в пилоте |

**Критерии перехода к интеграции:** базовая линия измерена на экспертной разметке; KPI по precision и FPR достигли согласованных целей; аналитики и ведомство подтверждают пользу; нет правовых и этических инцидентов.

## 8. Риски и меры

| Риск | Мера |
|---|---|
| Ложные срабатывания вредят невиновным авторам (новости, конкурсы, реклама) | решение всегда за человеком; формулировка «признаки, а не вердикты»; причины отклонения возвращаются в правила; процедура исправления |
| Precision на реальном потоке ниже синтетической из-за дисбаланса классов | теневой режим, калибровка порогов на реальной разметке, приоритизация очереди |
| Пропуски, которых никто не видит (отсеянное не просматривается) | регулярный аудит случайной выборки отсеянного; экспертный holdout |
| Схемы адаптируются: новый сленг, маскировка, перенос в медиа | активное обучение, ежемесячные версии правил, нормализация маскировки, второй этап на LLM, медиа-пул |
| Сетевая связь принята за доказательство общего владельца | в интерфейсе связь подана как индикатор; передача в ведомство требует решения человека |
| Правовые риски сбора данных | только открытые данные и соглашения; юрист в команде с этапа 0 |
| Утечка хранимых случаев | минимизация, маскирование, доступ по ролям, шифрование, журнал доступа |
| Перегрузка аналитиков | приоритет (риск, охват, сеть), калибровка порога, распределение очереди |
| Деградация модели | версии и проверка на holdout перед выпуском; модель добавляет только один ограниченный сигнал и не решает сама |
| Изменение разметки сайтов ломает расширение | переход на официальные API и коннекторы на этапе 2 |

## 9. Дорожная карта по измеренным слабым местам

| Слабое место (holdout, синтетика) | Вероятная причина | Шаги | Как проверим |
|---|---|---|---|
